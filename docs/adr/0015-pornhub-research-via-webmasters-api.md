# Pornhub как третья Platform исследования: Webmasters API и список через yt-dlp, без видео

Для одного из Format нужен исследовательский контур по Pornhub: какие ролики в нише набирают больше своей нормы канала и чем они упакованы. Решили сделать Pornhub третьей Platform рядом с YouTube и Instagram. Один ролик читается публичным Webmasters API (`/webmasters/video_by_id?id=<viewkey>`, без ключа и входа): название, длительность, просмотры, рейтинг (доля голосов «за», %), число голосов, время публикации, теги, категории, исполнители, сегмент, превью и 16 кадров предпросмотра. Список роликов канала API не отдаёт, поэтому его даёт yt-dlp (плоское извлечение `/<kind>/<slug>/videos`, только viewkey, без страниц роликов). Лайки считаются как `round(rating × ratings / 100)`, комментариев нет. Outlier score по тому же правилу, что на YouTube: просмотры против медианы своего канала.

Альтернативы отвергнуты: скачивание роликов (объём, смысла для упаковки нет, и в репо и на шаре такого быть не должно), разбор HTML страниц роликов (ломается при каждом изменении сайта и дороже по запросам), вход в аккаунт и куки (фаза входа отложена, см. ниже).

## Spike S1: какое время считать публикацией

Шесть роликов (2023–2026), API и страница каждого. `uploadDate` страницы — время загрузки (совпадает с unix-временем в первых 8 hex-символах viewkey, с разницей в минуты). `publish_date` API — время выхода в свет: круглые отметки вида `19:00:05`, `02:00:04`, на 4–16 дней позже загрузки. `video_date_published` страницы — только дата: у трёх свежих роликов она равна дате API, у трёх других — дате загрузки (или промежуточной). Часовой пояс API по этим данным не определяется: ни один случай не лежит у полуночи.

Решение: `published_at` = `publish_date` API, прочитанное как UTC; исходная строка хранится в `video.raw.api_publish_date`. Час публикации в отчёте `traits` поэтому приблизителен (возможный сдвиг на несколько часов). Для Outlier score это не важно: базовая линия берёт ролики старше 3 дней.

## Spike S2: список роликов канала

yt-dlp 2026.08.19 (`PornHubPagedVideoList`): порядок `/videos` по умолчанию уже «новые сначала» и совпадает с `?o=mr`; `?o=mr` на `/channels/…` стоит yt-dlp лишнего запроса («switch to fallback»), поэтому не используется. Страница около 40 роликов (5 читаются одной страницей, 45 — двумя), `playlistend` ленивый: читаются только нужные страницы. Несуществующий slug даёт пустой список без ошибки и без названия плейлиста: канал считается существующим, если в списке есть хотя бы один ролик, и его название — slug.

## Consequences

- Каналы: `pornhub.com/{model,channels,pornstar,users}/<slug>` или `ph:<kind>/<slug>`, ключ `<kind>/<slug>` в нижнем регистре, handle — slug. Ссылка на ролик в `add-channel` отвечает подсказкой про `watchlist add-reference`.
- Scout: первый проход читает 60 новейших роликов. Дальше список берётся с начала: 40, потом 80, 120… (до 200), пока в нём не появится ролик этого канала, опубликованный не позже чем за 20 дней до `uploads_through` (ролик выходит в свет до 16 дней после загрузки, а список, возможно, идёт по загрузке: ролик ниже уже прочитанного ещё может быть новым); каждое расширение перечитывает список целиком (40 → 200 стоит 1 + 2 + 3 + 4 + 5 = 15 страниц). `video_by_id` вызывается только для незнакомых viewkey, от старых к новым; каждый даёт строку и снимок. `uploads_through` сдвигается, только когда прочитаны все незнакомые ролики выше отметки, поэтому проход, оборванный квотой или ошибкой, дочитывает следующий. Первый проход читает 60 новейших целиком, даже если какой-то из них уже знаком. Если 200 роликов не дошли до точки остановки, читаются только эти 200, отметка сдвигается, а более старые новые ролики остаются непрочитанными. Знакомый ролик без канала (добавлен через `add-reference` или `fetch` до scout) получает канал из списка без вызова API. Ролик, которого API больше не знает (коды 2001/2002), пропускается; в `snapshot` он попадает в `missing`, другие ошибки — в `errors`. Snapshot перечитывает ролики каналов Watchlist за последние 30 дней, выборку автора и свои ролики, кроме тех, у которых уже есть снимок за последний час.
- Просмотры ролика старше 30 дней больше не обновляются (snapshot его не перечитывает) и замирают на последнем снимке; на медленном канале это может занижать базу Outlier score.
- Ключ YouTube для Pornhub не нужен: без ключа scout и snapshot пропускают только часть YouTube, как при Instagram.
- Квота: часовая корзина `pornhub` (скользящие 60 минут, 600 вызовов, `CF_QUOTA_PORNHUB`); `ph.video_by_id` и каждая страница списка `ph.list_page` — один вызов. HTTP 429 ставит корзину на паузу на час. Между вызовами в одном процессе не меньше секунды, один фиксированный User-Agent, без куки. Секреты не читаются.
- `fetch` никогда не качает видео: в папке Reference лежат `info.json`, `thumb.jpg`, `frames/01..16.jpg` и лист 4×4 `frames.jpg`. Карточка (`cf-reference-card/1`, схема та же) меряет упаковку (длина названия, доля заглавных, цифры, скобки, POV, эмодзи, теги, категории), время публикации (день и час UTC и местные) и счётчики; транскрипта, Shot log и OCR нет, `notes.media` объясняет почему. В анализе `hook.spoken_hook` = null, а `hook.formula` описывает название вместе с превью.
- Транскрипта нет, поэтому сводки хуков по речи для Pornhub пусты; вместо них `python -m cf.research traits <watchlist> --platform pornhub` сравнивает outliers со всеми Reference с оценкой: длительность, признаки названия, теги и категории (lift, не меньше 3 Reference), день и час, медианный рейтинг.
- В `video.raw` хранится только последний рейтинг и число голосов; история — только в снимках (просмотры и лайки). Схема store не меняется (V10), миграции нет: `PLATFORMS` в коде получил `pornhub`.
- Строки Pornhub живут в общем store (ADR 0014): второй человек видит Watchlist, ролики и карточки так же, как YouTube и Instagram. Отдельного профиля нет.
- Фаза входа (свой аккаунт, статистика своих роликов) отложена: в этой фазе нет ни логина, ни учётных данных.
- Версия yt-dlp, на которой проверено, записана в `cf.research.pornhub.YT_DLP_VERSION`; после обновления yt-dlp список проверяется заново.
